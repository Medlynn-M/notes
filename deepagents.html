DEEP AGENTS

  • A Deep Agent is an agent harness designed for complex, multi-step, long-horizon tasks. It combines a tool-calling model with planning, filesystem-backed work, context management, and delegation.
  • “Deep” describes the depth and duration of the task, not a deeper neural network architecture.
  • These notes follow the six modules in the Introduction to Deep Agents course, starting from fundamentals and moving toward full system design.

We will use one running example: an email intelligence system that extracts claim types, funding amounts, periods, statuses, and CBM details, then validates and reconciles the results.

1. Foundations: what is an agent?

  • LLM: a model that interprets input and generates text or structured decisions.
  • Tool: an executable function or API that lets the agent retrieve data or perform an operation. The framework executes the tool; the model only requests it.
  • Agent: a model operating in a loop that can choose actions, observe results, and continue toward a goal.
  • Agent harness: the runtime and supporting capabilities around the model: tools, state, execution, context handling, persistence, permissions, and controls.
  • A single LLM call is not automatically an agent. An agent has an action-taking loop and a way to observe action results.

The agent loop

Goal + context→Model chooses→Tool/action→Observe→Continue or finish

Remember: the model decides what should happen next; the harness and tools carry out the action and return the result.

2. Why Deep Agents?

  • Simple tasks can often be handled with one model call or a short tool loop.
  • Complex tasks may require many dependent steps, large amounts of evidence, intermediate artifacts, parallel subtasks, and recovery after interruption.
  • Long runs can exceed the model context window if all messages and tool outputs are kept in the prompt.
  • Deep Agents provides reusable capabilities so developers do not have to build every planning, filesystem, context, and delegation mechanism manually.
  • Use a simpler deterministic workflow when it is enough. More autonomy adds cost, latency, and failure modes.

3. Module 1 · Building a Deep Agent

Create and run an agent

  • The Python package is deepagents.
  • create_deep_agent() is the SDK entry point for assembling the agent harness.
  • The resulting agent is runnable and can be called with invoke or ainvoke.
  • Select a model that supports the required capabilities, especially tool calling. Define the task instructions and provide application-specific tools.
Python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="provider:model-name",
    system_prompt="You are a careful email analysis agent.",
)

result = agent.invoke({
    "messages": "Extract claim details from this email thread."
})

Core configuration concepts

  • model: model name or initialized chat model.
  • system_prompt: role, rules, workflow, and output expectations.
  • tools: application functions, integrations, or MCP-connected tools.
  • middleware: composable behavior added around agent execution.
  • subagents: specialist child agents available for delegation.
  • backend: where virtual filesystem operations are stored or executed.
  • Permissions and interrupts: control which operations are allowed and which require approval.

System prompt, user request, and tool description

ItemPurposeExample
System promptStable role, rules, constraintsNever write to production without approval.
User requestTask for this runExtract claims from this thread.
Tool descriptionExplains when/how a tool is usedRetrieve messages by conversation ID.

Messages, threads, state, and checkpoints

  • Message: one user, assistant, or tool interaction.
  • Thread: continuing execution/conversation identity; can be resumed when persistence is configured.
  • State: current run data such as messages, tool outputs, and application fields.
  • Checkpoint: saved snapshot of graph state for resumption, inspection, or approval workflows.
  • A checkpoint preserves execution progress; long-term memory stores reusable information across tasks.

Tools, MCP, and HITL

  • Tools should have clear descriptions, validated inputs, bounded behavior, and predictable outputs.
  • MCP (Model Context Protocol) is a standard way for applications to connect models/agents with external tools and data servers.
  • Human-in-the-loop (HITL) pauses a consequential action so a person can approve, reject, or edit it.
  • Use approval for sending external email, modifying production data, deleting files, or other sensitive side effects.

4. Module 2 · Execution Environment

  • The execution environment is the workspace where the agent performs actions. It is different from the model context window.
  • It may include a virtual filesystem, shell/code execution, tools, backend storage, permissions, and network access.
  • A filesystem backend does not automatically mean shell execution is available; execution depends on backend capabilities and configuration.

Filesystem tools

grepSearch file contents
  • Files are useful as working memory: store plans, drafts, evidence, and large intermediate outputs outside the active prompt.
  • The model can read only the relevant portions later, reducing context pressure while preserving detail.
  • The backend controls storage and lifecycle; do not assume files persist across runs unless configured.
  • Sandbox: isolated execution environment with controlled access to resources. It reduces risk but does not replace least-privilege credentials, network restrictions, or validation.
  • Use least privilege. Separate read-only analysis from write/execute operations and explicitly restrict subagent tools.

5. Module 3 · Context Management

Context window and context engineering

  • The context window is the token capacity available to a model call. It can include instructions, messages, tool descriptions, tool results, and intermediate content.
  • Long agent runs accumulate history and large tool outputs. Unmanaged context increases cost, reduces focus, and may exceed model limits.
  • Context engineering means selecting and organizing the information the model needs for its current decision.
  • Goal: provide enough relevant information, but avoid flooding the model with unrelated history.

Summarization and offloading

  • Summarization: compress earlier interactions while preserving decisions, constraints, current status, open questions, and next steps.
  • Offloading: move large results or detailed intermediate material into files; keep a pointer or short summary in context.
  • Summaries should not replace exact source data when later steps need exact amounts, IDs, or evidence. Keep those details retrievable.

Skills and progressive disclosure

  • A skill packages reusable instructions and domain knowledge, commonly in a SKILL.md file, with optional scripts and references.
  • Progressive disclosure: expose skill metadata first, then load full instructions only when relevant.
  • Skills contain reusable know-how; tools perform actions; memory stores reusable facts/preferences; context contains information for the current model call.

Memory and prompt caching

  • Memory is information intended to be reused across separate tasks or threads. Persistence depends on the configured storage/backend.
  • Keep memory concise, accurate, and maintained. Avoid storing secrets or unnecessary transient details.
  • Prompt caching can reuse stable prompt prefixes with supported providers/models, reducing repeated processing cost or latency. It is provider-dependent.

6. Module 4 · Delegation

  • Delegation means assigning a bounded subtask to a child agent (subagent).
  • The parent/supervisor decomposes the goal, assigns tasks, receives reports, validates them, and integrates the result.
  • Subagents can have focused prompts, tools, and separate context windows. Their work can be isolated from the parent context (“context quarantine”).
  • Delegation can improve parallelism and specialization, but introduces coordination overhead, extra model calls, and integration risk.

When delegation helps

  • Independent research or extraction tasks can run in parallel.
  • A specialist task needs a different instruction set or restricted tool access.
  • A child’s detailed tool history would otherwise overwhelm the parent context.

When not to delegate

  • The task is simple and child-agent overhead exceeds the benefit.
  • Subtasks are tightly sequential or require shared mutable state.
  • A child would lose critical context because its task boundary is unclear.

Subagent design rules

  • Give each child one clear objective, scoped input, relevant tools, and a defined output schema.
  • Ask for concise findings and supporting evidence, not a full transcript of its work.
  • Specify prohibited actions, such as no production writes.
  • The parent must reconcile conflicts and validate child results before finalizing.

A practical design is to parallelize independent evidence extraction, then use deterministic downstream logic to reconcile amount-period-status relationships. Avoid having independent agents overwrite shared production records.

7. Module 5 · Putting It All Together

End-to-end agent workflow

  1. Receive the goal and input data.
  2. Clarify constraints and expected output.
  3. Plan the work when the task is complex.
  4. Retrieve relevant data through tools.
  5. Offload large results to files.
  6. Delegate independent subtasks.
  7. Integrate and reconcile results.
  8. Validate against schema and business rules.
  9. Pause for approval before consequential actions.
  10. Persist artifacts and return the result.

Planning and task tracking

  • Planning is an explicit task list, not hidden model reasoning.
  • Tasks can be tracked as pending, in progress, and completed.
  • Planning helps with long tasks, progress visibility, and recovery; it is unnecessary for every simple request.
  • Deep Agents supports task-planning middleware; exact configuration can vary by package version.

Reliability patterns

  • Validate structured output with a schema (for example, Pydantic).
  • Make write operations idempotent so retries do not create duplicate effects.
  • Retry transient failures with bounded backoff; do not retry invalid business logic blindly.
  • Keep source identifiers and evidence for extracted facts.
  • Set explicit stop conditions, maximum steps/time, and model/tool budgets.
  • Separate analysis/draft tools from commit/production tools.
  • Design for checkpoint, resume, inspect, and safe rerun.

Observability and evaluation

  • Trace model calls, tool calls, subagent runs, and state transitions.
  • Track latency, token usage, retries, errors, tool outcomes, and completion quality.
  • Evaluate factual accuracy, schema validity, policy compliance, cost, and task success.
  • LangSmith can help trace and evaluate; it is not the agent orchestration runtime.

Your email intelligence architecture

Important: agentic does not mean “let the LLM decide everything.” Keep deterministic joins, deduplication, status precedence, schema checks, and production safety rules in code.

8. Module 6 · Managed Agents

Managed vs. self-hosted

Managed agent serviceSelf-hosted SDK
A platform operates some runtime/deployment infrastructure, such as agent hosting, sandboxes, lifecycle, or scheduling (depending on service).You assemble the harness with the SDK and own hosting, runtime, security, scaling, and operations.

Why choose managed?

  • Reduce infrastructure work for long-running agent deployments.
  • Use platform-provided execution and lifecycle features where available.
  • Focus more on agent behavior, tools, and evaluation.

What remains your responsibility?

  • Domain rules, task instructions, and acceptance criteria.
  • Tool permissions, credentials, data privacy, and tenant isolation.
  • Quality evaluation, human approval, cost limits, and observability.
  • Incident handling and safe behavior when tools or models fail.

Choose managed when reduced operational ownership is worth the service constraints and cost. Choose self-hosted when you need deeper runtime control or must fit an existing infrastructure/security model. Compare total operating cost, not only model-token cost.

9. Conclusion · Mental model

Deep Agents is a configurable harness that combines a tool-calling model with planning, filesystem-backed work, context management, delegation, and execution controls so it can complete complex multi-step tasks.

Before building a Deep Agent, ask

  • Is the task genuinely multi-step, or would a deterministic pipeline be simpler?
  • What decisions may the model make, and what must remain deterministic?
  • Which operations should be exposed as tools?
  • What belongs in context, files, and persistent memory?
  • Which subtasks are independent enough to delegate?
  • What permissions and approvals are required?
  • How will outputs be validated, traced, evaluated, and recovered?
  • What are the cost, latency, and stopping limits?
